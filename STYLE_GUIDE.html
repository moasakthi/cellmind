CellMind Design System

Tokens and components for the manufacturing-intelligence dashboard defined in DDD.MD. Grounded in the subject: the deep blue-black of a darkened EL inspection chamber, the glow of electroluminescence itself, and furnace-amber for anything that needs an engineer's attention.

Color

One accent, not a rainbow. Accent marks interactive/informational elements; furnace, danger and good are semantic only — they report state and are never used as decoration.

Ground & Ink

Paper--paper

Page ground. Cool-neutral, not pure white — pairs with the teal accent without competing.

Paper Raised--paper-raised

Cards, tables, inputs — one step above the page ground.

Ink--ink

Primary text. Near-black with a cold undertone — the color of a wafer under low light.

Ink Mute--ink-mute

Captions, timestamps, secondary metadata.

Accent — EL Glow

Accent--accent

Links, active nav, primary actions, selected states — the cyan-teal glow of an electroluminescence image.

Accent Soft--accent-soft

Info badge/banner fill.

Accent Ink--accent-ink

Text set on Accent Soft.

Semantic — Furnace / Danger / Good

Furnace--furnace

Medium-severity, warnings, needs-review — named for the F07 firing furnace, the BRD's own recurring defect source.

Danger--danger

High severity, conflicts, offline/failed states, destructive actions.

Good--good

Healthy yield, approved, online, passed holdout evaluation.

Typography

Two roles, both system-native by design: an OS-native UI face keeps a data-dense control-room dashboard fast and legible at small sizes — the same reasoning real SCADA/HMI software uses — and a monospace face is reserved for anything that is read as data: IDs, timestamps, percentages, code.

Accessibility

  • State is never color-only: every chip in Status & Badges carries a text label.
  • All interactive elements show a visible focus ring (outline in the accent color) — see any button or field above via keyboard Tab.
  • Body text targets ≥4.5:1 contrast against its surface in both themes; large numerals (KPI values) target ≥3:1.

Motion

Two motion budgets, not one. The product UI (this dashboard, admin consoles) keeps motion restrained and purely functional — an engineer scanning a dense batch table shouldn't compete with decoration. The public landing page is an editorial surface aimed at prospects and hackathon judges, where motion is the pitch's pacing device. Both are implemented in Framer Motion; the landing page additionally uses React Bits for decorative primitives (ambient glow, spotlight hover). See DDD.MD §16.1 for the full specification.

Tokens

--motion-fast120ms — press/hover feedback
--motion-base220ms — state transitions (chip color, meter fill)
--motion-reveal450ms — product-UI scroll entrance (single elements only)
--motion-hero650ms — landing-page hero sequence, per step
--ease-out / --ease-incubic-bezier(.16,1,.3,1) / (.7,0,.84,0) — exits run ~65% of the matching entrance

Framer Motion / React Bits mapping

  • Product UI — layout prop for list reordering, AnimatePresence for modal enter/exit only. Meter fills and stepper nodes animate via plain CSS transition, not a library — single-property changes don't need one.
  • Landing page — variants + whileInView (never animate on mount, so nothing above the fold competes at once); React Bits supplies the hero's animated text treatment, card spotlight-hover, and ambient background glow — all decorative, all no-op under reduced motion.

All motion — tokens, the demo above, and every Framer Motion/React Bits usage — is disabled outright (not shortened) under prefers-reduced-motion: reduce, since none of it carries information a static state change wouldn't.

Do / Don't

DoPair every status chip with its plain-language state (e.g. "HIGH · 91%"), per FR-14.
Don'tUse the furnace-amber or danger-red hues for anything decorative — they are reserved for real severity/warning states.
DoUse mono for anything the operator will scan as data: IDs, timestamps, percentages.
Don'tIntroduce a second accent hue — one accent keeps "what's interactive" unambiguous.
